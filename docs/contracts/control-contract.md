# Durable control contract

The original contract was written before implementation. The probe-hash passage is a 2026-08-30 post-audit amendment preserved alongside the original in Git history; it did not author the unchanged independent suite.

`src/run/index.ts` exports `openRunStore({path, clock?})`. It opens a real SQLite file; `clock` optionally supplies Unix milliseconds for deterministic deadline tests. Return methods below. `close()` closes the database. All public methods validate unknown input, reject unknown fields and return detached records. Timestamps and lease durations are safe integers. String identifiers are nonempty and unpadded. Policies follow public-contracts.md and must have a valid hash. Stored records survive close/reopen.

`createRun({projectId,policy,targetBuild,featureConfigHash,featureProbeHash?,targetFeature?,mode,projectConfigHash?,cleanupConfigHash?})` accepts `polar_sandbox | local_replay`; feature hash must match policy. `targetFeature`, when supplied, is the strict contract-v1 feature descriptor, its hash must equal `featureConfigHash`, and its ID must equal `policy.featureId`. `featureProbeHash`, when supplied, must equal the hash of the code-owned v1 probe rules resolved against that descriptor. The optional configuration hashes and probe fields remain readable for records created before their persistence. The product controller supplies all four bindings for every new run. The immutable approval binding includes the full configuration, scenario list SC01..SC04, and fixed limits of two users, one customer/checkout/subscription, 100 tool operations, 15 active minutes. Exactly one active run per project is enforced transactionally across connections. A conflicting run throws `ACTIVE_RUN_CONFLICT`. No external writes occur in this store.

The product controller treats missing legacy probe bindings as read-only records. `inspect_project`, reports, and cleanup remain available, but an active non-cleanup tool returns `FEATURE_PROBE_BINDING_REQUIRED`. Worker recovery, owner-approved continuation, and checkout continuation revalidate the exact project configuration plus the current schema-v2 Adapter Doctor receipt before rearming a TrueForge lifecycle session. The worker completes recovery before opening HTTP or MCP serving. Polar recovery also re-establishes its process-local sandbox preflight before any saved turn can issue a read or mutation. A blocked recovery records `RUNTIME_RECOVERY_BINDING_BLOCKED` and does not resume the runtime. Before it records operation intent for `prepare_fixture`, `change_test_subscription`, or `await_period_end`, the controller reruns Adapter Doctor and compares the current schema-v2 target ID, build, feature descriptor hash, and resolved probe hash with the approved run. A mismatch returns `RUN_BINDING_CHANGED` before target or provider mutation. Each feature observation repeats descriptor and probe-hash checks before the browser/API reads and again before recording evidence. These checks narrow deployment races; they do not atomically lock the staging deployment.

The product controller supplies `projectConfigHash`, a SHA-256 binding of repository, ref, target origin, Polar organization/product/price, a canonical digest of the explicit Polar test mailbox, model connection, runtime, and repair profile. It rejects changed configuration before approval or fresh lifecycle dispatch. It separately supplies `cleanupConfigHash`, limited to destinations cleanup can affect: target ID/origin for local replay, plus Polar organization/product/price for Polar runs. Unrelated mailbox, model, repository, runtime, or repair-profile drift cannot strand already-owned cleanup. Cleanup destination drift returns `CLEANUP_BINDING_CHANGED` before intent or mutation and remains retryable after the exact destination is restored. Legacy runs without the narrower hash require their original full configuration. `requestStop(runId)` changes an active run to `stopping` while retaining its project lock. The controller revokes the local MCP capability first, requests TrueForge cancellation on a best-effort basis, accounts for locally active effects, performs approved cleanup, then calls `cancelRun`. Runtime unavailability is recorded separately and cannot strand owned cleanup.

`getRun(runId)` returns its persisted record or throws NOT_FOUND. `decidePlan({runId,approvalId,bindingHash,decision:'allow'|'deny'})` requires the exact pending approval, matching binding, and current time strictly before 15-minute expiry. The controller first persists a `prepared` continuation containing that exact decision and binding, then changes the run, persists `dispatched` before calling TrueForge, and atomically records the confirmed turn with the new runtime cursor. Recovery may finish `prepared`; it reconciles `dispatched` through `findContinuation` and never redispatches an absent or uncertain continuation. A synchronous active-time check runs before each fresh TrueForge dispatch and recovered stream; an expired allow converges through stop and cleanup without dispatch. Credited external waits are no longer exempt. Allow changes status to running, deny to canceled and revokes the run capability after reconciliation. Repeating the exact same valid recorded decision returns the original result even after expiry; changing the decision throws APPROVAL_CONFLICT. Invalid binding or expiry throws APPROVAL_STALE, without consuming the approval. Denied plans cannot execute operations.

`claimOperation({runId,operationId,kind,args,approvalId,leaseMs})` accepts kind `prepare_fixture | change_test_subscription | await_period_end | probe_feature | cleanup_run`. args is a JSON object, rejecting accessors, cycles, classes, undefined/nonfinite values; maximum nesting32. leaseMs is integer 1..30000. Running + matching allowed plan required. Returns `{kind:'dispatch'|'confirmed'|'unknown'|'in_flight',operation}`. New records contain operationId, runId, kind, canonical validated args, argsHash, state, idempotencyKey, and receipt; legacy records can omit args. A new claim persists state dispatched BEFORE returning dispatch. Same ID and arguments while lease valid returns in_flight. Expired lease returns unknown and must never redispatch automatically. Confirmed returns its original receipt. Changed arguments OR kind for the same ID throw OPERATION_CONFLICT. Another run's operation ID must never expose its receipt or permit mutation. Use OWNERSHIP_MISMATCH for a cross-run operation ID. Stable idempotencyKey survives reopen. Active execution deadline is 15 minutes after plan approval, checked before new claims. At most 100 unique operations, retries do not increment. After stop, claims for new operations are rejected, including cleanup until cleanup has an explicit separate safe controller path.

`operations({runId,states?})` is a read-only, deterministic, run-scoped inventory. `abandonDispatched({runId})` is startup recovery only: it changes every surviving `dispatched` record to `unknown` once and emits `operation.unknown`; it never redispatches. Stop recovery blocks on an unknown resource-creating operation unless all possible identities are already inventoried. Unknown probe, wait, or cleanup operations may clean known resources, but remain visible in `operationReconciliation`. Legacy unknown records without args require manual review. A manual-review run deliberately retains its project lock and exposes no retry button that could only hit the same blocker. The operator first exports the report and preserves the control database, then correlates the saved run ID, operation ID, argument hash, and run-owned metadata against authoritative staging/provider records. Only owned effects may be cleaned. Because this release has no operator-attestation endpoint, it does not clear the unknown record; after external reconciliation, archive that database as the audit record and use a fresh configured control database for later work. Never edit an unknown operation into a success receipt.

`confirmedOperation({runId,operationId,kind,args})` is the read-only retry lookup used before mutable live-run checks. It returns only an exact confirmed operation or `null`. It works after completion, cancellation, or configuration drift. Reusing an operation ID with changed kind or arguments throws `OPERATION_CONFLICT`; another run's ID throws `OWNERSHIP_MISMATCH`. It cannot claim, dispatch, or confirm work.

An authenticated Polar checkout can place the runtime in `waiting_external`. The controller records one external-wait credit per persisted wait key and adds only that measured interval to the active execution deadline, capped at 24 hours. `externalWaitCredit({runId,waitId})` is a read-only lookup that returns the exact persisted `{startedAt,endedAt}` or `null`; controller recovery uses it if the store commit survived but the controller marker did not. The credit is exactly-once across restarts. No ordinary runtime, model, or provider latency receives this exemption.

`confirmOperation({runId,operationId,receipt})` accepts JSON receipt only for a matching dispatched or unknown operation. First confirmation persists receipt. Repeated identical confirmation is idempotent. Conflicting receipt throws OPERATION_CONFLICT; foreign run throws OWNERSHIP_MISMATCH. This can confirm an in-flight operation after cancellation, so its external effect is accounted for. No new dispatch is permitted after stop.

`cancelRun(runId)` records canceled, does not erase operations, releases the active-project lock, and is idempotent. A completed run stays completed. `finishRun({runId,verdicts})` accepts a running run and an array of verdicts defined in public-contracts.md; stores completed + aggregate outcome. This method is internal trusted-controller only, never an HTTP/model outcome setter. Empty verdicts are inconclusive. A completed run cannot be overwritten with different results. Terminal runs are immutable except confirmations of already dispatched effects, cleanup and linked repairs. Each serialized cleanup attempt receives a fresh two-minute deadline. Cleanup upserts the latest receipt by resource ID, so a successful retry replaces a stale `leftover` rather than hiding it later in an append-only list. Each target deletion persists a destination-bound per-resource intent before dispatch and a confirmed marker before updating the report; recovery adopts a confirmed marker without another DELETE and leaves a dispatched-only marker as `CLEANUP_OUTCOME_UNKNOWN`. The authenticated terminal cleanup route may retry other known leftovers, but it does not override an unknown external result without read-only reconciliation. Ordinary MCP operation claims remain closed after termination.

`events({runId,after})` returns append-only events with strictly increasing integer sequence, type, payload, occurredAt. after is a nonnegative safe integer, exclusive, supports reload without writes. All state transitions and first operation confirmations append events; duplicate decisions and receipts do not create duplicate state-transition events. Unknown run throws NOT_FOUND.

Failures are Error instances with a nonempty `code`; validation failures use INVALID_INPUT. Methods do not expose tokens or create external resources. Evidence validation and approval of repair publication will have separate contracts before testing.
