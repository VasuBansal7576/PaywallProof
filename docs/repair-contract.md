# Repair authorization and publication contract

This is the public contract for `packages/repair/src/index.ts`. Independent tests may use this document without reading implementation. All public JSON request objects reject unknown fields; factory dependencies and `publishRepair`'s store/adapter handles are trusted typed configuration. Errors have a stable `code`. No method executes a test or claims that supplied receipts prove more than their trusted collector observed.

## Proposal and verification

`openRepairStore({path,repository,allowedPaths,requiredRegressionChecks?,clock?})` opens durable SQLite storage. `repository` is an exact `owner/name`; `allowedPaths` is a nonempty list of exact repository-relative file paths, never glob patterns. `requiredRegressionChecks` defaults to `SC01`, `SC02`, `SC03`, `SC04`. `clock` defaults to Unix milliseconds. `close()` closes the database.

`store.propose(input)` accepts `{runId,findingId,attempt,baseCommit,baseBranch,repository,branch,policyHash,oracleHash,allowedPaths,changes,diffHash,verificationMode,failureCode,summary,reportUrl}`. Attempt is 1 or 2, unique per run/finding; attempt 2 requires attempt 1 to exist. Repeating identical input returns the same proposal; changing an existing attempt throws `REPAIR_CONFLICT`. Proposal IDs are generated. No receipts exist at this point and state is `proposed`.

Commit hashes are lowercase 40-character Git SHA-1 IDs; policy, oracle and diff hashes are lowercase SHA-256. `repairBranch(runId,findingId,attempt)` supplies the only accepted branch name. A change is `{path,content}` with UTF-8 content or `null` for deletion. `patchHash(changes)` hashes the canonical path-sorted change list using lexical UTF-16 path ordering, not a display-only unified diff. Empty, duplicate, case-colliding, file/descendant-conflicting, traversal, absolute, backslash, control-character or protected paths are rejected. Proposal paths must be contained in both the proposal and configured allowlists. Tests, oracle/core files, environment files, auth configuration, lockfiles and Git/CI configuration are protected even if accidentally allowlisted. Executable and symlink changes are unsupported.

`validateRepairPaths({checkoutRoot,paths,allowedPaths})` validates the exact file allowlist and walks existing filesystem components with `lstat`; symlinks and non-directory parents fail. Missing final files are allowed for additions. Call before reading/writing a disposable checkout, then use sandbox filesystem isolation to prevent concurrent replacement. This helper does not execute repository code.

`get(proposalId)` returns a detached record; `list(runId)` returns that run's proposals. Public record fields are `{id,createdAt,proposal,state,manifest,manifestHash,approval,progress,leaseToken,leaseUntil}`. `createdAt` is always the proposal's Unix millisecond creation time, including after later transitions. Initially manifest, manifestHash, approval and progress are null, leaseToken is null and leaseUntil is zero. Lease/progress fields are adapter bookkeeping, not owner authorization.

Protected path comparison is case-insensitive. Forbidden complete directory components are `.git`, `.github`, `.gitlab`, `.circleci`, `.buildkite`, `.codex`, `.agents`, `node_modules`, `tests`, `test`, `__tests__`, `core`, `oracle`, `oracles`. A filename starting `.env`, containing `.test.` or `.spec.`, ending `.lock`, or ending `-lock.json`, `.lock.json`, `-lock.yaml`, `.lock.yaml`, `-lock.yml`, `.lock.yml` is forbidden. Also forbidden are `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`, `bun.lockb`, `.npmrc`, `.yarnrc`, `.gitmodules`, `.gitlab-ci.yml`, `azure-pipelines.yml`, `Jenkinsfile`, and names starting `vitest.config`, `jest.config`, `playwright.config`. Auth settings means filenames starting `auth.`, `auth-`, `oauth.`, `oauth-`, `security.`, or `security-` and containing `config` after that prefix, such as `auth.config.ts`. An application implementation named `authentication.ts` is not blocked by its name alone; the trusted allowlist and review still apply. Filesystem validation rejects existing executable-mode files, symlinks and directory targets. Publication independently rejects edits to Git mode `100755`, `120000` or `160000`. A source filename ending `.sh` is not automatically executable; newly created files always use Git mode `100644`.

`store.recordVerification({proposalId,before,after,regressions})` is a **trusted verifier-only** API, never an HTTP/model evidence setter. Each receipt is `{id,executionId,checkId,oracleHash,policyHash,baseCommit,diffHash,artifactHash,observedAt,exitCode,outcome,failureCode}`. `failureCode` is a string for a failure and `null` for a pass. Before must fail with the proposal's exact failure code, nonzero exit code and a null diffHash. After must pass with exit zero and the proposed diffHash. Before/after use the same checkId. Every configured regression check must have a passing after-patch receipt. All receipts must match the same oracleHash, policyHash and baseCommit; each has a distinct ID, a nonempty execution ID, an artifact SHA-256 and collection time no earlier than the proposal. After/regression observations cannot predate before. No future receipts are accepted. Missing, failed or mismatched evidence leaves the proposal unverified. The verifier must independently bind these receipts to real executions and hash the collected artifacts; structural validation alone cannot establish that a test ran.

Successful verification creates a strict immutable `manifest` containing the proposal fields, configured required regression checks, and the supplied receipts. `manifestHash` is SHA-256 of that canonical manifest. State becomes `verified_local` or `verified_polar_sandbox`. Repeated identical verification is idempotent; changing verified evidence is rejected.

Malformed or missing receipt fields throw `INVALID_INPUT`. Structurally valid but failed/mismatched/incomplete verification throws `VERIFICATION_REJECTED`; the stored record remains unchanged and unverified. An already verified manifest cannot be replaced and throws `VERIFICATION_CONFLICT` for different evidence.

## Publication approval

`store.requestPublication({proposalId,title,body})` requires verified evidence. It creates one pending approval bound to the entire manifest and `{repository,baseBranch,branch,draft,title,body}`. `draft` is always true for `local_replay`, false for `polar_sandbox`. The provider body appends a deterministic repair marker, report link, verification mode and receipts. The record returned includes the exact final publication arguments and `bindingHash`. Approval expires after 15 minutes. State is `awaiting_publication`.

The return value is the whole record described above, not an approval alone. Its `approval` is `{id,bindingHash,expiresAt,decision:'pending',args:{repository,baseBranch,branch,draft,title,body}}`; there is no top-level `args` or `bindingHash`. `approval.args.body` is the final generated body, not just the submitted preamble. `manifest` and `manifestHash` remain unchanged. Repeating identical title/body returns the same approval and expiry. Changed publication arguments throw `APPROVAL_STALE`; `VERIFICATION_REQUIRED` is returned when no manifest has been verified.

`store.decidePublication({proposalId,approvalId,bindingHash,decision})` accepts `allow` or `deny` for the exact pending approval before expiry. Exact repeated decisions are idempotent; conflicting decisions, changed bindings and stale approvals fail. Denial makes the attempt `abandoned`; a fresh attempt/proposal is required to change a denied patch. Approval never invokes GitHub.

`publishRepair({store,adapter,proposalId,approvalId})` is the only controller entry for publication. A durable lease serializes publication across store connections. An allowed, unexpired, exact approval is checked immediately before each GitHub write. In-flight or uncertain operations cannot be bypassed by a fresh operation ID. Expired approvals may reconcile existing remote objects by reads, but cannot create anything new. A changed remote base branch, conflicting repair branch/tree/commit or mismatched PR stops publication. No force push, merge, deployment or branch deletion exists.

## GitHub adapter and recovery

Construct `new GitHubPublicationAdapter({repository,token})` for production. The token stays in the trusted adapter, never in manifests, SQLite or sandbox inputs. Requests use only `https://api.github.com/repos/<configured repository>/...`, reject redirects, cap response size and have a 30-second deadline. No automatic HTTP retry occurs. GitHub API version is `2026-03-10`.

For isolated fault injection only, construct with `{repository,transport:{kind:'synthetic',request}}` instead of a token. `request({method,path,body?})` returns `{status,body}` with method GET or POST and paths relative to the configured repository, such as `/git/ref/heads/main`. Synthetic transport receipts are explicitly marked `synthetic`; they never set a proposal's state to `published` or count as provider evidence. Do not expose transport selection to model tools.

The adapter reads the configured base ref, Git commit and complete recursive tree; computes the exact expected file map using Git blob hashes; rejects symlink/submodule/executable changes; creates a tree and deterministic commit; and reads them back. It creates only the deterministic repair branch and re-reads its commit/tree. Existing matching branches are recovered; mismatches are never overwritten. Creating a tree/commit again is content-addressed, and a branch creation has a unique deterministic ref.

Before a PR POST, persist that dispatch may occur. Query all PRs for the exact head/base and deterministic marker; a matching existing PR is read and recovered, including after a lost response. If a PR POST may have happened but no matching PR is visible, return `PUBLICATION_OUTCOME_UNKNOWN` and perform reads only on future attempts. Never issue another PR POST merely because the previous response was lost. Read the final PR and branch before returning a `published` receipt. A local replay PR must remain a draft. Changes to destination, commit, marker, draft status or publication text invalidate recovery.

`publishRepair` returns `{kind:'published'|'synthetic',receipt}`. Receipt contains repository, branch, baseCommit, commitSha, treeSha, PR number/URL, draft, manifestHash, collectedAt and transportMode. Only `kind:'published'` records the `published` state. A synthetic result remains `awaiting_publication` and is never reusable through the real transport.

## Limitations

No generated code, oracle, patch test or remote publication is performed by this store. Until a real sandbox verifier supplies qualifying receipts, preparation remains `proposed`. Unknown external outcomes require read reconciliation or owner intervention. Path protections supplement review; they cannot prove that arbitrary code changes preserve authentication or signature verification.

The Git data implementation follows official [tree](https://docs.github.com/en/rest/git/trees), [commit](https://docs.github.com/en/rest/git/commits), [reference](https://docs.github.com/en/rest/git/refs) and [pull request](https://docs.github.com/en/rest/pulls/pulls) APIs. GitHub permissions, Actions execution and hosting costs remain operator responsibilities; this package does not enable workflows or purchase services.
